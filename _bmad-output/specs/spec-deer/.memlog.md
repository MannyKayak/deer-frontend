Structured pre-sorted inputs — trusting authored separation.
- (note) Why: neo-laureati in farmacia struggle to *remember* the 3000 official public-exam questions, not to access them. Deer pairs each question with a mnemonic. This slice is a no-login validation funnel (landing + 10-question taste quiz), not the full product.
- (capability) CAP-1 (FR-1): Hero with CTA to quiz. Intent: visitor sees headline/subheadline/CTA/microcopy/trust-bar and starts the quiz in one tap, no intermediate step. Success: click on primary CTA lands on question 1/10 directly; sticky header CTA always reachable on scroll.
- (capability) CAP-2 (FR-2): Comparison section (traditional method vs Deer). Intent: visitor reads the mnemonic differentiator before committing to the quiz. Success: two-column comparison renders single-column on mobile, two-column desktop+, with the fixed copy pair (traditional vs Deer box).
- (capability) CAP-3 (FR-3): Minimal footer. Intent: visitor can find product name and legal links. Success: footer shows 'Deer — mnemotecniche per il concorso farmacie' plus Privacy/Termini links (link targets pending OQ-3).
- (capability) CAP-4 (FR-4): In-page quiz preview. Intent: visitor sees a non-interactive sample question card before deciding to start. Success: preview card uses same quiz-card component/format as the real quiz but has no clickable options and never reveals a mnemonic via interaction.
- (capability) CAP-5 (FR-5): Single-question presentation. Intent: visitor answers one official question at a time with category tag, progress ('Domanda N di 10'), and 3-4 full-width option buttons. Success: next question never visible until current is answered; no login/personal data required.
- (capability) CAP-6 (FR-6): Answer reveal + mnemonic unlock. Intent: on tap, visitor immediately sees which option was correct and the associated mnemonic. Success: correct option always highlighted regardless of user's choice; mnemonic box appears with 'Mnemotecnica' tag; correctness never conveyed by color alone (NFR-1); advance to next question only via explicit 'Conferma' tap, no auto-advance.
- (capability) CAP-7 (FR-7): No mid-quiz server persistence. Intent: quiz progress lives only in-browser. Success: a page refresh mid-quiz returns visitor to question 1; no Supabase record is created for intermediate answers, only for full completion (FR-11).
- (capability) CAP-8 (FR-8): Result + mnemonic recap. Intent: after Q10, visitor sees their score and all 10 mnemonics encountered (not just correct ones). Success: score shown as 'N/10 corrette'; all 10 mnemonics listed regardless of correctness.
- (capability) CAP-9 (FR-9): Feedback box. Intent: visitor can leave a quick reaction on the experience. Success: 5-level star rating, optional, never gates the rest of the final screen; feedback event sends independently of whether email is filled.
- (capability) CAP-10 (FR-10): Optional email capture. Intent: visitor can leave an email for launch updates without it being required. Success: field clearly marked optional; only blocking validation is email format; a separate consent checkbox must be checked before an entered email is actually submitted, but the checkbox never blocks the completion event itself (GDPR consent copy pending OQ-3).
- (capability) CAP-11 (FR-11): Quiz-completed event write. Intent: system records exactly one completion event per finished quiz. Success: single Supabase (EU-Frankfurt) record per completion with score + optional feedback + optional email + server-stamped timestamp; zero records for abandoned quizzes; score is server-recomputed from submitted answers, never trusted from the client; write happens through one Server Action only, Supabase secret key never reaches the browser.
- (capability) CAP-12 (FR-12): Cookieless analytics. Intent: system tracks landing visits, quiz starts, and quiz completions without a cookie banner. Success: visit_landing, quiz_started, quiz_completed events fire through a single tracking wrapper (lib/analytics/track.ts); quiz_completed fires only after the Server Action returns {ok:true}, never optimistically; no consent banner shown; mid-quiz abandonment tracking is best-effort, non-blocking.
- (constraint) Stack fixed (AD-1, project-context.md DECISO): Next.js App Router 16.2.12 + TypeScript + Tailwind CSS v4 on Vercel; Supabase Postgres EU-Frankfurt; cookieless analytics (Plausible or Umami, OQ-4); Stripe and Refine backoffice explicitly out of scope this slice.
- (constraint) Server-first Islands paradigm (architecture spine): Server Components by default (app/, components/landing/); Client Component islands only for components/quiz/ and components/feedback/; no 'use client' at page level.
- (constraint) Exactly one server write per quiz (AD-2): no network write between Q1 and final screen; single completion write on finish. Bends design: rules out any per-question save-for-safety pattern.
- (constraint) Static content stays in repo, not DB, this slice (AD-3): 10 questions+mnemonics are versioned data files; no question/mnemonic Supabase table yet. All reads go through one accessor module lib/content/index.ts (AD-6) — no component reads the raw data file directly.
- (constraint) Score integrity (AD-5): Server Action (lib/actions/submitQuizCompletion.ts, 'use server') receives raw answers (questionId->selectedOptionId), recomputes score server-side, never trusts a client-sent score; completedAt stamped server-side; Supabase secret key (service_role or sb_secret_...) read only from server env, never NEXT_PUBLIC_-prefixed; RLS denies all but this key.
- (constraint) Quiz state is client-memory only (AD-7): question index/answers/revealed mnemonics live in useState/useReducer inside the quiz island; no per-question route segment (rules out /quiz/[step] which would let refresh resurrect progress via URL).
- (constraint) Analytics funneled through one wrapper (AD-9): all tracking calls go through lib/analytics/track.ts against a fixed event list in lib/analytics/events.ts; no component calls the Plausible/Umami SDK directly.
- (constraint) Design tokens are Tailwind theme, not CSS vars (AD-10): DESIGN.md colors/type/spacing/radii registered under theme.extend; no var(--token) arbitrary values for tokens already in theme. Visual system is fully owned by DESIGN.md/EXPERIENCE.md (adopted companions) — this spec does not restate component visuals.
- (constraint) Single Supabase project, no dev/prod split this slice (AD-11): one EU-Frankfurt project serves local dev, Vercel Preview, and production; accepted trade-off that Preview submissions land in the same table as production.
- (constraint) Accessibility (NFR-1): correct/incorrect state never conveyed by color alone — always paired with icon or text; WCAG 2.1 AA contrast on DESIGN.md palette.
- (constraint) Privacy (NFR-3): email + feedback stored in Supabase EU (Frankfurt) per GDPR; no data collected without explicit consent (consent checkbox gates only the email portion, FR-10/FR-11).
- (constraint) Budget ceiling (project-context.md): ~5-6k EUR build, ~1.5k EUR/year recurring — drives 'as simple as correctly possible' choices (one table, no auth, no second environment, no custom CI/CD).
- (constraint) Account ownership: all infra accounts (Supabase, Vercel, analytics, domain) must be titled to the Product Owner, not the dev team (project-context.md).
- (decision) Non-goals (PRD S6, explicit): no login/account/personal area this slice; no full 3000-question DB (10 placeholders only); no timed 100-question simulation or streak/countdown/weak-area dashboard; no admin backoffice (Refine is later phase); no payments/Stripe; no cross-session/cross-device quiz progress persistence; no mascot (flagged TBD in design system, not decided).
- (decision) Success signal, primary: SM-1 quiz completion rate (Q1 starters reaching final screen) target >=50%, validates CAP-5/6/7. SM-2 email opt-in rate (of completers) target >=20%, validates CAP-10.
- (decision) Success signal, secondary: SM-3 average quiz completion time, sanity-checks the '2 minutes' copy claim. SM-4 feedback star-rating distribution, informative only, no numeric target.
- (decision) Success signal, guardrail: SM-C1 — perceived mnemonic quality (via SM-4) must not degrade while optimizing SM-1; a high completion rate bought by dumbing down questions or dropping the mnemonic would be a false validation signal.
- (assumption) Consent copy for email opt-in not yet supplied by any source (candidate: Iubenda) — placeholder needed until OQ-3 resolves; blocks nothing structurally (AD-5 seam absorbs it) but blocks real launch.
- (assumption) No quantitative performance budget (Lighthouse/Core Web Vitals) set; Server-Component-default (AD-8) judged sufficient for this 4-page slice without a formal target.
