- (direction) Source: in-chat task brief 2026-10-13 (/bmad-spec args), rich and pre-sorted - express distill, no elicitation. Slug chosen by spec: home-hero-content. Scope: front-end side only (this repo); table, migration, RPC and admin form are built in remindeer-backoffice.
- (decision) Why: backoffice gains a Contenuti pagine section where an admin edits per-page content; only home exists. Hero copy, stats and image are hard-coded in components/landing/hero.tsx today and app/page.tsx fetches nothing, so / is static.
- (decision) Driving requirement: content is never fetched from the browser - a client fetch shows an empty hero in flight and hides content from search engines. Page is served as complete HTML and stays as fast as now: fetch on server, cache so / stays static, regenerate on content change.
- (capability) CAP-1 Hero content from the backoffice. Intent: the home hero shows title, subtitle, CTA label, CTA note, stats and hero image authored in the backoffice. Success: with the RPC returning content, / renders those values and view-source contains title, subtitle, CTA and stats text; no browser request fetches page content.
- (capability) CAP-2 Default content fallback. Intent: the hero always renders complete content whatever the content source does. Success: on RPC error, null, or unexpected shape the hero renders the current copy and mascot image unchanged; a single missing or empty field falls back to its own default while valid fields are kept; failures are logged on the server; / never fails to render.
- (capability) CAP-3 Variable stats row. Intent: the hero shows the 0 to 4 stats the admin defined. Success: N valid stats render N items in the existing markup; zero stats render no stats row at all, not an empty container.
- (capability) CAP-4 Editable hero image as LCP. Intent: the hero shows the admin-chosen image, or the mascot when none is chosen, without layout shift. Success: remote image loads from the public page-images bucket with eager loading and high fetch priority; hero_image null renders the static mascot at 1213x1217; the image box keeps a stable size before a remote image of unknown dimensions loads.
- (capability) CAP-5 Static home with cached content. Intent: the home page stays statically rendered while its content comes from the database. Success: production build output reports / as static, not rendered per request; cached content refreshes by itself within about one hour even if no webhook arrives.
- (capability) CAP-6 On-demand revalidation. Intent: a content change in the backoffice reaches the public home page without a redeploy. Success: POST /api/revalidate returns 401 without the correct secret; with it, the tag of the slug in the webhook body is revalidated and the next render of / shows the new content.
- (capability) CAP-7 Operator documentation. Intent: a human can finish the setup this repo must not perform. Success: repo docs state REVALIDATE_SECRET and the exact webhook setup - URL, header name, table, events.
- (constraint) No client-side fetching of page content and no loading state for the hero.
- (constraint) Hero layout, classes, CategoryTag text and CTA target /quiz are not editable and stay exactly as they are; quiz flow, other landing sections and visual design are untouched.
- (constraint) Data funnel: one server-only function in lib/data/ returns the home content; no component calls Supabase directly (same discipline as lib/data/questions.ts, lint-enforced).
- (constraint) RPC JSON is untrusted input, validated at the lib/data boundary; contract: supabase.rpc(get_page_content, {p_slug: home}) with the publishable key, returns one object or null (shape in page-content-contract.md).
- (constraint) hero_image.path resolves to SUPABASE_URL/storage/v1/object/public/page-images/path. No signed URLs: they expire after one hour and cannot live in a cached page. The Supabase storage host must be allowed in next/image config.
- (constraint) Cache the content fetch under a per-slug tag (page-content:home) plus a time-based revalidation of about one hour as safety net for a missed webhook.
- (constraint) Revalidation endpoint: shared secret read from a request header and compared to env REVALIDATE_SECRET; slug read from record.slug, falling back to old_record.slug. Trigger is a Supabase Database Webhook on page_contents because the backoffice is a browser-only SPA and cannot hold a secret.
- (constraint) This repo creates or alters no database object (schema belongs to remindeer-backoffice). If the contract is insufficient: stop and report, no workaround.
- (constraint) The implementer does not create the Supabase webhook nor change hosting settings; exact steps are written down for a human.
- (constraint) Stop condition: if deployment is a pure static export (no server runtime), on-demand revalidation cannot work - stop and report before implementing CAP-5 and CAP-6.

- (constraint) Tests in __tests__/ (existing Vitest setup) cover fallback logic - error, null, malformed JSON, missing fields, zero stats - and the route handler auth check. Lint, typecheck and tests pass.
- (constraint) Implementation report states: what changed, RPC live or built against contract, hosting and whether it supports on-demand revalidation, manual steps left (env var, webhook), contract interpretations.

- (decision by user) OQ-2 resolved 2026-10-13: keep last good content. A failed read (RPC error, network, exception) is never stored in the cache, so previously cached content keeps being served and the read is retried; hard-coded defaults are used only when no good content was ever cached.
